# 사람의 테스트를 받는 시점

2026-10-02. 사용자 질문: “나의 테스트는 어느 단계에서 이루어져야 하지?”, “아까 … 링크는 뭐야? 지금 해보는 게 의미가 있나?”

**물리 개발 전체가 끝날 때까지 기다리지 않는다.** 의미 있는 작은 변경이 같은 상태/입력의 비교와 필요한 회귀·모바일 실행 검사를 통과하면, 그 변경만 선택형 A/B로 공개해 체감 피드백을 받는다. 다음 구현은 그 피드백과 독립적으로 계속한다. 새 메이저 변경을 일반판 기본값으로 올리는 결정은 사용자가 비교한 뒤 한다.

## 기존 비교판의 최신 판정

- [팔 근력 비교](https://yoonjl-svg.github.io/halfsword-codex/feature-lab.html#arm-comparison): 세이버 또는 큰 양손검의 A/B. 양쪽 검객의 어깨·손목 명시적 토크를 기존 최종 한도에 맞추는 차이다. **새 native 팔꿈치 한도 시험은 아니다.** 무게감, 위/아래로 움직일 때 차이, 멈추기와 입력 반응을 본다. [배포 근거](../strike/arm_capacity_trial_release.json).
- 절삭 반작용 비교는 사용자가 자세/동작 붕괴와 “득보다 실이 컸다”를 보고하여 **재시험 권유를 중단**했다. 이전 [배포 근거](../strike/cut_reaction_trial_release.json)는 당시 실행 가능성의 증거이며 최신 수락 실패를 취소하지 않는다. 로컬 안내를 고쳐도 인증 복구/배포 전에는 기존 공개 버튼이 남는다. 원인과 후퇴 관문을 수정한 뒤에만 다시 안내한다.

두 비교판은 **새 기립/옆 미끄럼·베기 끝점·전신 물리의 완성판이 아니다.** 마지막 코드 연결 검사는 [옵션 모바일 8조건](../strike/arm_cut_mobile_round1.md)이며 모바일 에뮬레이션과 실제 휴대폰 체감은 구별한다. 팔 B→절삭 B 이동에는 팔 제어 차이가 있었고 검술 보정은 저장값에 의존했다. 후속 비교는 같은 무기·팔·보정·난이도를 명시한다. 이전 그립 반작용은 사용자 피드백 뒤 이미 paired 기본값에 반영됐다. 철회한 지지 연구판을 새 후보처럼 다시 안내하지 않는다.

## 새 기립 후보의 전달 상태

21:02 KST 기준 [기립 마찰 기록 수정](../strike/stance_memory_trial.md)은 로컬 실제 게임 연결·전투·모바일4조건 검사를 마쳤다. **아직 배포하지 않았다.** GitHub API 인증401로 전송이 막혀 기존 공개 페이지에는 새 기립 비교가 없다. 환경의 독립 저장소용 인증을 복구하고 Actions·공개 모바일 실행까지 확인한 뒤 새 링크를 안내한다. 기존 팔/절삭 링크로 이 수정의 체감을 평가하지 않는다.

## 짧은 피드백 순서

1. 한 무기로 A와 B를 각각 짧게 플레이한다. 아래로 베기, 아래에서 올리기, 휘두르다 멈추기를 같은 의도로 시도한다. 절삭 비교에서는 실제 적중 전후를 본다.
2. 어느 쪽이 자연스러운지, 차이가 없는지, 어떤 동작이 어색한지만 알려도 된다. “차이가 거의 없다”도 유효한 결과다. 사용자가 오류 장면이나 설정을 정확히 특정해야 개발을 진행할 수 있는 구조로 만들지 않는다.
3. 피드백은 **링크/후보 범위와 함께** 기록한다. 팔 비교의 체감을 기립 후보 승인으로 해석하지 않는다. 알려진 공중 발사·새 제어 상실 등은 개발 측에서 먼저 걸러낸다.

새 후보 안내에는 바뀐 점 한 가지, 기존판/후보 링크, 볼 동작, 남은 한계를 붙인다. 체감 비교가 가능하다는 말과 일반 적용 승인을 받았다는 말을 구분한다.
