# 누운 자세에서 치솟는 지지 연구판: 철회와 원인 분리

2026-10-02 KST. 사용자 보고: “연구판 해봤는대, 누워 있다 갑자기 허공으로 치솟는다거나, 이상한 동작들로 에러가 나.” 공개 후보를 철회했다. **수정 후보도 회복 검증에 실패하므로 다시 공개하지 않는다.** 일반 지지는 legacy, 수용된 그립은 paired를 유지한다.

## 공개 조치와 검증 누락

철회 소스 `b6483ea65f6ff4097b2386493ee9487f711527d4` → 독립 main `c8a179be5f9d25746d8ac17d415fc8db6ce068ab`, 전송 [36894369678](https://github.com/yoonjl-svg/halfsword-codex/actions/runs/36894369678), Pages [36894534092](https://github.com/yoonjl-svg/halfsword-codex/actions/runs/36894534092) 성공. 기존 `physicsTrial=support` 직접 주소도 `withdrawn=true`, `active=false`, legacy 지지로 전환하고 철회 안내를 표시한다. 후보 CTA를 없앴다. 이미 열린 이전 페이지는 다시 열거나 새로고침해야 새 코드를 받는다.

[공개 검증 기록](support_withdrawal_public_metrics.json): HTML 네 파일과 실행 JS HTTP200·배포 바이트 일치, 실제 모바일 크기에서 시작/드래그/해제/재시작과 일반 URL 복귀, JS/HTTP 오류0. 이 검사는 연결·입력·철회를 확인하며 물리 안정성 전체나 실제 기기 체감을 보장하지 않는다.

기존 `support_transfer_probe`의 기립은 `knockDown(false)`로 바로 getup에 들어갔다. 바닥 제거 down 시험은 있었지만 **바닥 위에서 실제로 누워졌다가 일어나는 경로**가 빠졌다. 30초 AI 대조도 down 진입이 없었다. 유한값·내부 순힘0·마지막 stand만으로 공개 판단을 내린 검증 범위가 부족했다.

## 재현과 확인된 결함

실제 Fighter/Combat/Rapier와 1/120초 실행을 사용했다. legacy 준비3초 뒤 `knockDown(true)`, 바닥 유지, 무입력25초를 관찰했다. 손상은 한쪽 다리 controller health .45 또는 양쪽 .2를 직접 설정한 합성 조건이다. 신체 자세·속도를 주입하지 않았다. 원판 건강/편측 손상은 골반이 각각 .215/.192m까지 낮아지고 가슴이 크게 기울어 실제 누움이 확인됐다. seed7/17의 궤적은 같으므로 독립 표본 두 개로 세지 않는다.

원판 axial은 건강/손상에서 stand 이후 다시 getup으로 2/3회 돌아갔고, 실제 지면 solver 접점이 모두 없는 최장 구간은 .208/.217초였다. 골반 최고 높이 약1.012/1.010m·상향속도1.736/2.062m/s였다. **사용자가 본 큰 발사 장면을 같은 조건으로 완전히 재현했다고 주장하지 않는다.** 반복 회복과 짧은 도약은 재현했다.

새 힘쌍 계산은 수직 요구력을 다리 축의 수직 성분 `ny`로 나눴다. 다리가 거의 수평이면 `ny→0+`에서 최대 축력으로 포화되고, `ny<=0`에서는 갑자기0이 됐다. 낮은 근육 활성에서도 상한은 그대로였다. 실제 원판 건강 getup의 근육 .1166·ny .062에서 한 다리 축력이 1,841.8N에 도달했다. 해당 순간의 일률은 음수였으므로 그 표본 자체를 양의 에너지 폭주로 부르지 않는다.

격리된 연구 코드에서 다음을 수정했다.

- `T=min(cap, desired*ny)`로 수직 요구를 축에 투영하여 수평에 가까워질수록 연속적으로0이 되게 한다. 부족한 수직 힘을 별도 외력으로 보충하지 않는다.
- 축력 상한에도 실제 muscle을 적용한다. 건강·하중에 따른 기존 상한과 구별하며 인체 근력 실측값이라고 부르지 않는다.
- down/dead에서는 이 가상 다리 신전 힘쌍을 사용하지 않는다.

축력 교정23·그립/URL12·접촉12와 빌드를 통과했다. 기존 legacy 건강/편측/양측 손상 궤적은 수정 전후 exact였다. 이 결과는 확인된 계산 결함의 수정이며 기립 해결 판정이 아니다.

## 같은 누운 상태에서 비교한 결과

수정을 낙하 시작부터 적용하면 낙하 자체도 바뀌어 건강 조건은 충분히 낮게 눕지 않았다. 그래서 원판 제어로 건강2.2초/손상2.8초까지 자연 낙하한 뒤 회복 제어만 바꿨다. 두 분기의 native world snapshot·몸/제어 상태가 일치하고, 원판 분기의 전체 궤적도 최초 재현과 exact인 것을 먼저 확인했다. 이때 골반은 .215/.196m였다.

| 동일 누움 이후 | 건강 원판 → 수정 | 편측 손상 원판 → 수정 |
|---|---:|---:|
| stand 이후 재넘어짐 횟수 | 2 → 0 | 3 → 3 |
| 최장 지면 접점 없음(s) | .208 → .117 | .217 → .100 |
| 최고 골반 상향속도(m/s) | 1.736 → 1.432 | 2.062 → 1.324 |
| 최고 골반 높이(m) | 1.012 → .982 | 1.010 → .939 |

도약 감소와 건강 조건 개선은 관찰했지만 **부상 회복의 반복 실패가 남아 재공개 불가**다. 전체 낙하부터 바꾼 비교에서 재넘어짐0만 취하면 잘못된 개선 결론이 된다. [같은 누움 관문과 지표](same_lying_recovery_summary.json), [전체 진단 지표·원자료 해시](support_launch_incident_metrics.json)를 함께 본다.

## 기각한 단순 해법과 다음 설계

동일 원판 제어로2초 넘어지다가 upright만 끄거나 힘쌍과 함께 끄면 골반이132.6/24.9m까지 발사되고 관절 앵커 간격이44.7/58.6m까지 벌어졌다. 유한값을 유지해도 신체 연결이 붕괴한 실패다. 독립 감사에서 관절 삭제/재생성이나 전체 근육 변경 없이 기존 upright의 k/d만0으로 한 것을 확인했다. 이것은 **단순 보정 제거의 실패**이며, 공개판 그대로의 발사 재현이나 유일한 에너지원 특정이 아니다. 2초 시점은 골반 .599m의 크게 기울어진 down으로, 위의 낮게 누운 비교와도 구별한다.

현재 getup→stand는 시간만으로 진행한다. 같은 누움에서 기존 관찰용 기하 조건을 충족할 때까지 stand 전환만 막는 진단도 해 봤다. 건강/손상 모두25초 끝까지 getup에 갇혔고 골반 .759/.165m였다. **관찰 문턱 하나를 제어에 붙이는 해법도 기각**한다. 이 변경은 게임에 넣지 않았다. 해당 비교의 한 raw 제어 해시는 WASM 메모리 주소 두 개 때문에 달랐고, native snapshot/physicalControl 및 주소만 제외한 의미 상태는 exact였다. portable 관문은 주소를 제어 상태에서 제외한다.

다음 설계는 누움→손/무릎 지지→체중 이동→다리 신전→보행 인계의 실제 접촉과 제어 목표를 함께 다룬다. native 관절 모터의 감쇠/목표속도는 현재 `j.max`의 총토크 제한 밖에 있으며, upright·접촉 일도 아직 직접 계측하지 못했다. 하중 이전과 관절별 실제 한계를 계측·분리한 뒤 회복 제어를 고친다. 속도/높이 강제 제한이나 화면 보간으로 증상을 가리지 않는다.

재개 조건에는 실제 누움·부상·충돌을 포함한 반복 회복, 관절 연결 유지, 설명되지 않는 공중 도약/에너지 급증 없음, 기존 조작 회귀와 모바일 플레이를 포함한다. 숫자 유한·stand 진입만으로 통과시키지 않는다. 큰 지지 변경의 일반 적용은 기존 사용자 확인 조건을 유지한다.
